Data reference

GEP publishes the same events in two forms: hourly files in Cloud Storage (gs://gep-archive), which are the archive of record, and tables in BigQuery (gep-archive.gep), loaded from those files every hour.

Keys and time

  • Event key. GitHub restarted its event ids on 8 October 2025 in two sequences, one for Push, Create and Delete events and one for all other types, and ids of 2026 repeat ids of 2020 and 2021. Within GEP an event is identified by (id, type); across archives that cover earlier years, by (id, type, created_at).
  • Arrival hour. Each event is filed in the UTC hour in which GEP first received it. Push, Create and Delete events often reach the feed hours after their created_at; some events carry a created_at days or years earlier.
  • Partition date. event_date is the date of created_at, or the date of arrival when created_at is missing, later than the arrival, or more than 24 hours before it (backdated marks the last case).

BigQuery

All tables are in the dataset gep-archive.gep (location US). events and the four typed tables are partitioned by event_date and require a filter on it.

BigQuery bills a query by the columns it reads. A dry run reports the whole payload column as the upper bound, while a query that reads single fields of payload is billed far less than that bound. The typed tables hold the fields of the most common event types as columns and are the least expensive way to read them.

Typed tables

Each typed table holds the events of one type with these columns first: event_id, created_at, event_date, backdated, archive_hour, repo_id, repo_name, actor_id, actor_login, org_login. Since October 2025 GitHub sends smaller payloads for pull request and push events (GitHub changelog); the typed columns carry what the feed still sends.

events_gharchive

A view of events with GH Archive's columns: type, public, payload (a JSON string), repo, actor and org (records), created_at, id (a string) and other, plus event_date and archive_hour. Queries written for that layout run against it with a new table name and a filter on event_date. Reading payload through the view reads whole payloads.

Example queries

Events by type on one day:

SELECT type, COUNT(*) AS events
FROM `gep-archive.gep.events`
WHERE event_date = '2026-11-18'
GROUP BY type
ORDER BY events DESC;

Status and completeness of recent hours:

SELECT hour, status, events, est_exposure_rate_git, est_exposure_rate_other, est_capture_rate
FROM `gep-archive.gep.hours`
WHERE hour >= '2026-11-18'
ORDER BY hour;

One payload field, read from the JSON column:

SELECT JSON_VALUE(payload.action) AS action, COUNT(*) AS events
FROM `gep-archive.gep.events`
WHERE event_date = '2026-11-18' AND type = 'IssuesEvent'
GROUP BY action
ORDER BY events DESC;

Pull request actions in one repository over a week, from a typed table:

SELECT action, COUNT(*) AS events
FROM `gep-archive.gep.pull_requests`
WHERE event_date BETWEEN '2026-11-12' AND '2026-11-18'
  AND repo_name = 'microsoft/vscode'
GROUP BY action
ORDER BY events DESC;

A query in GH Archive's layout:

SELECT repo.name AS repo, COUNT(*) AS stars
FROM `gep-archive.gep.events_gharchive`
WHERE event_date = '2026-11-18' AND type = 'WatchEvent'
GROUP BY repo
ORDER BY stars DESC
LIMIT 20;

Events of complete hours only, by joining hours:

SELECT e.type, COUNT(*) AS events
FROM `gep-archive.gep.events` AS e
JOIN `gep-archive.gep.hours` AS h ON e.archive_hour = h.hour
WHERE e.event_date = '2026-11-18' AND h.status = 'ok'
GROUP BY e.type
ORDER BY events DESC;

Files in Cloud Storage

The bucket gs://gep-archive uses Requester Pays; every request needs --billing-project=YOUR_PROJECT (gcloud) or userProject (API). List with a prefix or a wildcard, for example 'gs://gep-archive/raw/2026/11/18/*'.

raw/YYYY/MM/DD/YYYY-MM-DD-HH[.vN].ndjson.gz        the events of one arrival hour, one line per event
keys/YYYY/MM/DD/YYYY-MM-DD-HH[.vN].keys.gz         the hour's keys, sorted "id type" lines
variants/YYYY/MM/DD/YYYY-MM-DD-HH[.vN].ndjson.gz   other contents received for keys that had more than one
manifests/YYYY/MM/DD/YYYY-MM-DD-HH[.vN].json       the hour's manifest; its presence means the hour is sealed

Version 1 of an hour has no suffix and is never overwritten. A correction is a new version (.v2, .v3) whose manifest gives the reason. A version that only revises the completeness measurement replaces the manifest and keeps the earlier data files, which its manifest names.

Event lines

Each line wraps the event exactly as GitHub returned it in an envelope; lines are sorted by (created_at, id):

{"gep":{"v":1,"observed_at":"2026-09-26T07:07:40.547123Z","poller":"a","tick":41152,"req":123456,"page":1,"pos":17,"sha":"9f2c61d04a7be311","seen_by":["a","b"]},"event":{...}}
  • event: the event object as GitHub returned it, key order kept. Taking .event of each line gives one event per line.
  • observed_at: when the response that first contained the event was received; poller, tick, req, page, pos: which collector, read, page and position.
  • sha: first 16 hex digits of BLAKE2b over the event with sorted keys. seen_by: every collector that received the event. variants: present when other contents were received for the same key.

Manifests

A manifest records the hour's identity and provenance (hour, version, supersedes, reason, sealed_at, gep_version, api_version), the files written with their SHA-256 checksums, the event counts by type and by id sequence, the spread of arrival lags, per-collector statistics, the status with its reasons, and the completeness measurement: snapshots read per page, and per sequence the ids seen, the covered id span, the estimated events unexposed and missed, and the exposure and capture rates. Example: manifest of 2026-11-19, 17:00 UTC.
